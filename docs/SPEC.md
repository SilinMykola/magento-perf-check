# Magento Performance Rules: technical specification

> Design specification of the tool. Owner: Mykola (Magento 2 backend, 8+ years, core contributor).
> Code, README, rule documentation, commits: English.
> Project name: `magento-perf-check` (package `silin/magento-perf-check`, repository [SilinMykola/magento-perf-check](https://github.com/SilinMykola/magento-perf-check)).

---

## 1. Goal

A static analyzer that finds **performance and Full Page Cache anti-patterns** in Magento 2 / Mage-OS code before they reach production. It also takes design and compatibility rules that an official source states, such as the Technical guidelines or a change in a Magento release ([ADR 8](adr/0008-scope-beyond-performance.md)). Principles:

1. **Works without configuration.** `composer require --dev`, one command, an immediate result.
2. **Precision over quantity.** A noisy tool gets switched off within a week. A rule with low precision does not enter the default set until it is calibrated (section 7).
3. **Every finding teaches.** Why it is bad, what to fix, a "bad / good" example, a link to the primary source.
4. **Lives in existing pipelines:** PHPStan, GrumPHP, CaptainHook, GitHub Actions, GitLab CI, coding agents.

---

## 2. Source policy (mandatory)

Every output of the tool must rest on a verifiable primary source. This is the main argument for trust: the author is not widely known, so authority comes from links, not from a name.

| Level | What counts | Role |
|---|---|---|
| **A** | Official Adobe documentation (developer.adobe.com, experienceleague.adobe.com), including the Technical Guidelines. For Hyvä-specific rules, the official Hyvä documentation | sufficient to include a rule |
| **B** | Magento core code (a link **to a specific commit**, not to a branch, so the link does not go stale) and magento/magento2 issues with a confirmed reproduction or measurements | sufficient to include a rule |
| **C** | Blogs, community documentation, agent skills, third-party standards (ECG and the like) | supplementary explanation only, **never the sole basis** |

Rules:
- A rule enters the default set (✅ or ⏳) only if it has at least one level **A or B** source. A rule with only C sources stays 🧪 until an A/B source appears.
- Links to core code are pinned to a commit. Current base: `magento/magento2@a385d02f` (2.4-develop, 2026-10-16). When the base is updated, the links are rechecked by a script in CI.
- Each rule page (`docs/rules/<ID>.md`) has a **Basis** section: which sources, of which level, and in one sentence what exactly in the source confirms the conclusion (a quote of up to 15 words or a paraphrase).
- The README must have a **"What our rules are based on"** section: this policy, a link to the rule table with source levels (in `docs/rules.md` since M3), a link to `docs/calibration.md` (measured precision) and an honest caveat that static analysis gives heuristics, not a guarantee: every finding is a reason to check, not a verdict.
- The message of every finding contains a link to the rule page, where the sources are visible.

## 2a. Existing tools and how we differ

| Tool | What it covers | Limitations |
|---|---|---|
| [magento/magento-coding-standard](https://github.com/magento/magento-coding-standard) (phpcs) | one performance rule: `Magento2.Performance.ForeachArrayMerge`. Plus related ones: Proxy and Interceptor in the constructor, ObjectManager and `$this` in templates, discouraged functions (`sleep`, `session_*`) | no FPC or N+1 rules |
| [magento-ecg/coding-standard](https://github.com/magento-ecg/coding-standard) (phpcs) | `Ecg.Performance.Loop` (load/save/delete/getFirstItem and composite type methods in loops), `CollectionCount`, `GetFirstItem`, `FetchAll`, `Sql.SlowQuery`, `ObjectManagerUsage` | **tokens without types**: any `->get()` in a loop counts as a violation. Last commit in 2024-08. Does not check XML |
| [bitExpert/phpstan-magento](https://github.com/bitExpert/phpstan-magento) (PHPStan, about 2.9 million installs) | type extensions for factories, proxies and magic methods. 5 architectural rules (service contracts, collections through a factory, `setTemplate` in blocks) | no performance or FPC |
| Core integrity tests (`dev/tests/static/testsuite/Magento/Test/Integrity`) | including `DBSchema/PrimaryKeyTest` | only for core code, not run on projects |
| [run_as_root/magento-cli-auto-proxy](https://packagist.org/packages/run_as_root/magento-cli-auto-proxy) | runtime: injects Proxies into CLI command constructors | not static |
| Adobe Marketplace EQP Varnish test | dynamic MISS → HIT test on pages | not static, Marketplace only |

**How we differ:**
- PHP rules on PHPStan: they know the **type** (this is a `Collection`, a `ProductRepositoryInterface`, a `SessionManagerInterface`), not the method name. That means an order of magnitude fewer false positives than ECG.
- **An XML and FPC layer that nobody else has:** layout (`cacheable`, `ttl`), `sections.xml`, `events.xml`, `di.xml`, `.graphqls`, `communication.xml`, `queue_consumer.xml`, `crontab.xml`, `indexer.xml`/`mview.xml`, `db_schema.xml`.
- We do **not implement** rules that duplicate MCS (section 4.9).

## 3. Architecture

One Composer package, two subsystems, one entry point.

```
vendor/bin/magento-perf-check            ← one command for the user
   ├── XML analyzer (our own, DOM)        → X-* rules, and J-* rules on storefront JavaScript
   ├── PHPStan with our extension         → P-* rules
   └── Reporter: merged report, shared rule IDs, baseline, formats
```

### 3.1 PHPStan extension (`type: phpstan-extension`)
- Registers automatically through [phpstan/extension-installer](https://github.com/phpstan/extension-installer). It can also be included manually in the project's `phpstan.neon` if the project already uses PHPStan.
- The rules work at any PHPStan level (custom rules do not depend on the level).
- bitExpert/phpstan-magento is used for the types of proxies and magic methods; this package types factories itself. Whether it is a dependency or a recommendation is decided in an ADR in M0. **Check compatibility with PHPStan 1.12 and 2.x** (section 8).
- Each rule has a PHPStan identifier (`magentoPerf.loopModelLoad` and so on) for `@phpstan-ignore` and the baseline.
- **Loop context:** a NodeVisitor marks nodes inside `foreach`/`for`/`while`/`do`, and inside closures passed to `array_map`, `array_walk` and a collection's `->walk()`. Cross-method analysis (a loop calls a method that loads a model) is done in M4 through PHPStan Collectors.

### 3.2 XML analyzer
- Scans `app/code`, `app/design` and, when enabled by a flag, third-party packages in `vendor` (not `magento/*`, not `mage-os/*`).
- Parsing through DOM/XPath. Each rule receives the file, the area and the module.
- Storefront JavaScript (`.js` files and the `<script>` elements of `.phtml` templates under `view/frontend`, `view/base` and `design/frontend`) is read by a scanner of string literals, with their property paths, and comments, not a parser ([ADR 9](adr/0009-storefront-javascript-scanned-by-the-xml-analyzer.md), [ADR 10](adr/0010-property-paths-in-the-script-scanner.md)).
- Area detection: `etc/di.xml` = global, `etc/frontend/di.xml` = frontend, and so on.
- For rules that need an XML ↔ PHP link (observer → class, plugin → methods), the XML analyzer builds an index, and the PHP side is checked by PHPStan against that index (passed through extension parameters or a temporary file).

### 3.3 Common
- **Config** `magento-perf-check.neon` (or a section in `phpstan.neon`): paths, disabling rules, severity override, handle allowlist for `cacheable="false"`, custom hot events and methods.
- **Suppression:** PHP through `@phpstan-ignore magentoPerf.xxx (reason)`. XML through a comment `<!-- perf-ignore X-LAY-01: reason -->` before the element. JavaScript through a comment `// perf-ignore J-DEP-01: reason` that ends on the line of the finding or the line before. The reason is mandatory.
- **Settings:** `C-*` rules read `app/etc/config.php` from its tokens, never run it, and only while such a rule is enabled ([ADR 11](adr/0011-settings-read-from-config-php.md)). Magento rewrites the file and keeps only its own section comments, so a finding there is suppressed by disabling the rule or by the baseline.
- **Baseline:** `magento-perf-check --generate-baseline` for legacy projects. New violations are caught, old ones do not get in the way.
- **Formats:** table (default), JSON, Checkstyle, SARIF 2.1.0, GitHub annotations, GitLab Code Quality.
- **Exit codes:** `0` clean, `1` there are findings at the `--fail-on` level (default `error`), `2` tool error.
- **`--project=<path>`:** analyze a project by path without installing into it (section 9a, CI).

## 4. Rule catalog

Legend:
- **Sev**: `error` (almost certainly a problem), `warning` (a likely problem, needs review), `info` (a recommendation).
- **FP**: false-positive risk (low / med / high).
- **MVP**: ✅ in the first release, ⏳ after calibration, 🧪 experimental (off by default).
- **Source**: levels A/B/C per section 2. (doc) a documentation page; (code) core code or an existing standard. 🔎 means an A/B primary source still has to be found: without it the rule does not leave 🧪.

## 7. Precision calibration (mandatory before a public release)

1. **Corpus:** Magento core (`app/code/Magento`), Mage-OS and the 20–30 most-downloaded open-source Magento 2 modules on Packagist (`type: magento2-module`, sorted by downloads). Fix the exact list in M2.
2. **Manual review of a sample:** up to 30 random findings per rule, each marked true positive / false positive.
3. **Thresholds:** a rule with severity `error` must reach ≥ 90% precision, `warning` ≥ 75%. Below the threshold the rule is lowered in severity or moves to 🧪.
4. **Metrics** are published in `docs/calibration.md` (corpus, version, precision per rule). This is an argument for trust for users.
5. **Real findings in open-source modules** are sent to the authors as PRs with a fix and a mention of the tool. This is the main distribution channel.

## 8. Compatibility and quality

- PHP 8.1+ (the minimum PHP for Magento 2.4.6). Analyzed code: calibrated on Magento 2.4.9; also ran on `module-cms` of 2.4.0, 2.4.3 and 2.4.4 from its own clone (`docs/runs/older-magento.md`), Mage-OS.
- **PHPStan 1.12 and 2.x.** Checked on a clean Magento 2.4.9: the project's `composer.json` `require-dev` contains `"phpstan/phpstan": "^1.9"`, and `composer.lock` has 1.12.33. An extension for PHPStan 2.x only will not install into a standard project without changing that constraint. In M0, decide in an ADR: support both major versions (shared rule code, adapters) or 1.12 as the minimum. Check the constraints in 2.4.4–2.4.8 and Mage-OS.
- In the same 2.4.9 installation: `nikic/php-parser` v5.8.0, `magento/magento-coding-standard` 40, `squizlabs/php_codesniffer` 3.13.5.
- Tests: for each rule, fixtures with positive **and negative** cases (looks like a violation but is not). For PHP through PHPStan's `RuleTestCase`, for XML golden tests.
- PHPStan max level on our own code, CI on a matrix of PHP versions.
- Semantic versioning. Adding a rule to the default set counts as a minor change and goes into the changelog, because users' CI may start failing.

## 9a. Development environment

- Repository: [SilinMykola/magento-perf-check](https://github.com/SilinMykola/magento-perf-check), developed on macOS with PHP 8.5 and Composer 2.10 on the host.
- Test Magento: a Composer project of Magento 2.4.9 on DDEV, written as `/path/to/magento-2.4.9` in this repository (PHP 8.4 in the container, Mutagen). Vendor is synced to the host.
- **The tool runs on the host against the Magento folder**, without being installed into the project: `php bin/magento-perf-check --project=/path/to/magento-2.4.9`. Static analysis needs neither the container nor the database.
- **Do not install the package into a Magento project through a Composer path repository with a symlink.** Mutagen in DDEV syncs symbolic links in portable mode, and a link from `vendor` out of the project may not sync. The Composer install check is done in M3 in a separate copy of the project, through a path repository in copy mode (`"symlink": false`). In M3 a path repository turned out to mirror the whole development checkout, including the git-ignored `var/`, so the check installed the `git archive` zip instead, which is what Packagist serves ([`docs/runs/m3-install.md`](runs/m3-install.md)).
- That is why the `--project=<path>` option is mandatory from M0: it also provides the CI mode of running without installing the module.
